# 0004 front matter の最小スキーマ

- 状態: Accepted
- 日付: 2026-10-04

## 背景

知識を機械可読にしたい一方で、投稿のハードルを上げたくない。現時点では、どの分類が有効か、どんなメタデータが実際に使われるかが分かっていない。

## 決定

YAML front matter を全知識ファイルに付ける。ただし**必須は `id` / `type` / `title` の3つだけ**とし、残り（`status` / `tags` / `related` / `sources` / `episodes` / `created` / `updated`）は任意とする。

仕様は [docs/metadata.md](../metadata.md) に記述し、**将来変更しうることを明記する**。

## 理由

- `id`・`type`・`title` があれば、一覧生成とリンク解決ができる。機械可読性の最低線はここ
- 統制語彙（タグの一覧を固定する、など）は作らない。何が必要かは、投稿が集まってから分かる
- 厳格なスキーマ検証は、GitHub に不慣れな人の投稿を弾く。検査は「壊れたリンク」「id の重複・不一致」といった、**放置すると後から直せなくなるものに限る**

## パーサの選択

front matter の読み取りは、`scripts/build_catalog.py` 内の最小パーサで行う。PyYAML などの外部依存を入れない。

- 理由: このスクリプトは CI とローカルの両方で動く。依存ゼロなら `python3 scripts/build_catalog.py` だけで誰でも実行できる
- 代償: 対応するのは「文字列・日付・フラットなリスト」のみ。ネストしたマッピングやブロックスカラーは読めない
- 必要になった時点で、PyYAML への切り替えを検討する（その場合は新しい ADR を書く）

## 帰結

- front matter に書かれた未知のキーは、検査では無視され、`catalog.json` には含まれない。将来フィールドを追加するときは、スクリプト側を更新する
- スキーマ変更時は、既存ファイルの一括更新が必要になる。ファイル数が少ないうちは手で、増えたらスクリプトで行う
- `status: reviewed` は「内容が正しい」という意味ではなく、「読める・公開情報として問題ない」ことの確認済みを意味する（[docs/metadata.md](../metadata.md)）
