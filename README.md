# Software Exploration Patterns

ソフトウェア開発における「探索知」を、分野をまたいで共同で蓄積・更新するオープンな知識ベースです。

要求工学 / ソフトウェアテスト / QA / アジャイル / Product Management / UX・UX Research / ソフトウェア設計 / Safety・Reliability Engineering に散らばっている「気づき方」の知識を、特定の方法論の所有物にせず、横断的に整理することを目指します。

- サイト（読む）: <https://kosuke-fujisawa.github.io/software-exploration-patterns/>
- 参加する: [CONTRIBUTING.md](CONTRIBUTING.md) / [Issue から投稿](https://github.com/kosuke-fujisawa/software-exploration-patterns/issues/new/choose)
- 運営の考え方: [GOVERNANCE.md](GOVERNANCE.md)

## このプロジェクトは何か

要求・QA・テスト・アジャイル・UX・PdM などに散らばる「探索知」を共同で集める、オープンな知識ベースです。

ここでいう探索知とは、たとえば次のような活動に関する知識を指します。

- 何かがおかしいことに気づく
- 前提を疑う
- 不明点を見つける
- 詳しい人に聞く
- 現場を見る
- ユーザー体験を確認する
- Failure State から逆算する
- リスクを見つける
- 要求・設計・実装・テスト・運用のどこで扱うべきか問い直す
- 理解を更新する

## なぜ作るのか

ソフトウェア開発では、要求・仕様・ユーザー理解・リスク・品質について、最初から完全に正しい理解を作ることはできません。

重要なのは、固定された要求を精緻に分析することだけではなく、ズレ・未知・リスクに早く気づき、理解を更新していくことです。

そのための知識は現在、複数の分野に分散しています。同じ気づき方が、分野ごとに別の名前で語られていたり、どこにも書き残されていなかったりします。このリポジトリは、それらを一か所に持ち寄って比較・統合できるようにします。

## 基本思想

### 正解集ではない

ここに掲載するものは「この通りにすれば正しい要求が得られる」という手順書ではありません。

不確実な状況で、

- 次に何を見れば理解が進むか
- 何を疑えばよいか
- 誰に聞けばよいか

を考えるための知識です。掲載されている内容が、あなたの状況で有効とは限りません。

### 探索は反復する

探索は一度で終わる作業ではなく、次のように反復します。

```text
理解する → 疑問が生まれる → 情報を取りに行く → 理解が変わる → 次の探索先が変わる
```

### テストに限定しない

テストは保証手段の一つにすぎません。

見つけたリスクに対しては、要求変更・設計変更・実装上の制約・静的検査・自動テスト・可観測性・運用・モニタリングなど、テスト以外の手段のほうが適切な場合があります。「どこで受け止めるのが妥当か」を問い直すこと自体が探索知です。

### 共同知識である

これは特定個人の方法論を公開するリポジトリではありません。

誰でも、新しい知識を提案し、既存の知識を修正し、反例を加え、出典を補い、重複を指摘できます。長期間かけてコミュニティが育てる Living Knowledge Base として運営します。

## 何を集めるか

| 種類 | 内容 | 場所 |
|---|---|---|
| **Episodes** | 実際に起きた出来事や経験。パターンとして整理できていなくてよい | [episodes/](episodes/) |
| **Heuristics** | 探索するときに役立つ短い判断則 | [heuristics/](heuristics/) |

| **Sources** | 既存研究・書籍・論文・記事・方法論 | [sources/](sources/) |

この4分類自体も暫定です。運用してみて合わなければ変えます。

## 参加方法

GitHub に慣れている人にも、慣れていない人にも参加してほしいと考えています。

- **Issue から気軽に経験を投稿する** — [新しい探索知を提案する](https://github.com/kosuke-fujisawa/software-exploration-patterns/issues/new/choose)。パターン形式に整理する必要はありません。エピソードだけでも歓迎します
- **既存パターンへ意見を送る** — 「実際に使えた」「違和感がある」「反例がある」なども、同じく Issue から送れます
- **Pull Request で直接編集する** — 追加・修正・出典追加・反例追加
- **出典だけの共有も歓迎** — 「この話はすでに○○で論じられている」という指摘は、再発明を防ぐうえで価値があります

詳しくは [CONTRIBUTING.md](CONTRIBUTING.md) を読んでください。

## 公開してはいけない情報について

> 顧客名、会社名、個人情報、非公開仕様、内部URL、認証情報、案件固有の詳細など、公開してはいけない情報を書かないでください。実務事例は一般化・抽象化して投稿してください。

CI で簡易的な Secret Scan を実行していますが、これは補助にすぎません。最終的には人間のレビューと、投稿する人自身の確認が前提です。

## LLM から使う

この知識ベースは、人間が読むだけでなく LLM から利用することを前提に作っています。Markdown を一次情報とし、1ファイル1知識単位、HTML だけに情報を閉じ込めない構成にしています。

サイトのビルド時に、以下の機械可読な成果物を生成しています（リポジトリにはコミットせず、サイト上にのみ存在します）。

| URL | 内容 |
|---|---|
| `/catalog.json` | 全エントリのメタデータ一覧 |
| `/patterns.json` | パターンのみのメタデータ一覧 |
| `/all-patterns.html` | 全パターンの本文を1ページに連結したもの |
| `/llms.txt` | [llmstxt.org](https://llmstxt.org) 形式の目次 |
| `/llms-full.txt` | 全知識の本文を連結したプレーンテキスト |

ローカルでは次のコマンドで同じものを生成できます（Python 3.9 以上、外部依存なし）。

```bash
python3 scripts/build_catalog.py
```

想定している使い方の例:

- 「この仕様について適用できる探索パターンを提示して」
- 「この要求に不足している情報を指摘して」
- 「次に誰へ何を確認すべきか考えて」

## ローカルで読む

Markdown が Source of Truth なので、クローンしてエディタで読むだけで内容は完全に読めます。サイトの表示を手元で確認したい場合のみ、GitHub Pages と同じ環境を入れてください（任意）。

```bash
gem install github-pages
jekyll serve
```
