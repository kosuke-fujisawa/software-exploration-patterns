# 値の意味を問う

> このパターンは検証されていません。反例や、適用できなかった状況の報告を歓迎します。

要求や仕様に具体的な値（60人、30秒、99.9%、10MB）が現れたとき、その値をそのまま境界として扱う前に、**その値が何を守るために存在するのか**を確かめる。

## Context

- 仕様書・要求一覧・チケットに、根拠の書かれていない数値が含まれている
- その数値をもとに、境界値分析・性能試験・バリデーション実装などを始めようとしている
- 数値を書いた人が、その場にいない、または当時の経緯を覚えていない

## Problem

数値は、それ自体がテストしやすい形をしているため、**意味を確かめないまま作業に入りやすい**。

しかし値には少なくとも次のような由来があり、由来によって必要な保証がまったく違う。

- 物理的・技術的な制約（これを超えると壊れる）
- 契約・法令・規格上の約束（これを超えると違反になる）
- 業務上の運用想定（今のところこれで足りている）
- 誰かの経験則、または仮置き（根拠がない）

由来を確かめないと、「59人・60人・61人」を丁寧に確認したのに、**本当に困るのは人数ではなく同時操作数だった**、というような取り違えが起きる。値が後から変わったときに、どこを見直せばよいかも分からなくなる。

## Forces

- 数値はテスト設計の入口として扱いやすく、すぐ着手できてしまう
- 「なぜこの値なのか」を聞くことが、仕様への疑義や能力への疑いと受け取られることがある
- 由来を知っている人がすでに異動・退職していることがある
- 聞いても「昔からそうなっている」としか返ってこないことがある

## Solution

値を使う作業を始める前に、次を確認する。

- **誰が決めたか** — 発注者か、設計者か、運用か、規格か
- **何を根拠に決めたか** — 計測結果か、契約か、推定か、仮置きか
- **この値を超えると何が起きるか** — 壊れるのか、遅くなるのか、違反するのか、誰も困らないのか
- **この値が変更された場合、何を再検討する必要があるか** — 値に連動して見直すべき設計・テスト・運用はどこか

重要なのは、**「超えると何が起きるか」が答えられないとき、それ自体が発見である**という点。その場合、守るべきものがまだ特定できていない。

答えが得られない場合は、値を確定した仕様としてではなく、**未決定事項**として扱い、記録に残す。

## Consequences

得られること:

- 本当に守るべき対象（人数ではなく同時操作数、など）が見つかることがある
- 値が仮置きだった場合、早い段階で確定させられる
- 値が変わったときの影響範囲が分かる
- テストの対象が、数値そのものから「守りたいもの」へ移る

失うこと・副作用:

- 確認のための時間がかかる。相手の時間も使う
- 「決まっていることを蒸し返している」と受け取られる場合がある

効かない場面:

- 値が規格・法令で外部から与えられており、由来を問うても変えられない場合（ただし「超えたら何が起きるか」は依然として有用）
- 値の由来が明確に文書化されており、確認コストのほうが大きい場合
- 探索の時間がまったく取れず、まず動くものを確認すべき局面
