# Patterns

複数の経験で再利用できる程度まで整理された探索パターンを置く場所です。

**ここにあるものは完成された方法論ではありません。** 現在置かれているのはすべて初期サンプルであり、実務での検証を経ていません。反例・修正・適用できなかった報告を歓迎します。

## 一覧

| パターン | 一言でいうと |
|---|---|
| [値の意味を問う](value-meaning.md) | 具体的な値を見たら、その値が何を守っているのかを先に確かめる |
| [知っている人に聞く](ask-the-expert.md) | 資料から推測を組み立てる前に、すでに知っている人を探す |
| [現場を見る](observe-the-field.md) | 文書だけでは分からない運用・環境・ユーザー行動を、実地で確かめる |
| [失敗状態から戻る](start-from-failure-state.md) | 「何をテストするか」ではなく「何が起きたら困るか」から遡る |
| [リスクを設計へ返す](return-risk-to-design.md) | テストで受け止める前に、設計・実装で消せないかを検討する |

## 書き方

[`_TEMPLATE.md`](https://github.com/kosuke-fujisawa/software-exploration-patterns/blob/main/patterns/_TEMPLATE.md) をコピーして使ってください。本文の構成は次を基本とします。

- **Context** — どんな状況で使うか
- **Problem** — そこで何が困るか
- **Forces** — 対立する力、やりにくくしている事情
- **Solution** — 何をするか
- **Consequences** — 何が得られ、何を失うか。**効かない場面も書く**
- **Related Patterns** — 関連するパターン
- **Sources / Episodes** — 出典と、もとになった経験

**この形式を厳密に守る必要はありません。** 埋まらない項目は空のままで構いませんし、書きにくければ別の見出しを使っても構いません。形式を整えることより、知識が残ることを優先します。

パターンとして整理しきれていない段階のものは、[`../episodes/`](../episodes/) に置いてください。

## パターンになる前の段階

```text
episodes/     実際に起きたこと（整理されていなくてよい）
    ↓ 繰り返し観測される
heuristics/   短い判断則
    ↓ 文脈・帰結まで言語化できる
patterns/     再利用できる探索パターン
```

この流れは一方通行ではありません。パターンに反例が集まって heuristic に戻ることも、分割されることもあります。
