# リスクを設計へ返す

> このパターンは検証されていません。反例や、適用できなかった状況の報告を歓迎します。

大量のテストが必要になったとき、**その複雑さをテストで受け止める以外に、要求・設計・実装の側で消せないか**を検討する。

## Context

- テスト設計をしていたら、組み合わせや状態の数が急激に増えた
- 「これを全部確認するのは現実的ではない」と感じている
- 削減技法（直交表、ペアワイズ、同値分割）で件数を減らす方向に進もうとしている

## Problem

テスト件数の爆発は、**テスト設計の問題として現れるが、原因はたいていテストの外にある**。

- 状態を持ちすぎている
- 設定の組み合わせが、実際には必要とされていない自由度まで許している
- 型や制約で表現できることを、実行時の検査に任せている
- 要求自体が、本当は不要な場合分けを含んでいる

ここで削減技法だけを適用すると、**複雑さは残したまま、確認だけを薄くする**ことになる。リスクは減っていない。

## Forces

- テストを担当する立場からは、設計や要求に手を入れる提案がしにくい
- 設計変更には、実装のやり直しと説明のコストがかかる
- 工程が分かれていると、「もう設計は終わっている」と言われる
- 一方で、テストの件数は目に見えるため、削減の圧力は強くかかる

## Solution

件数が爆発したら、減らす前に一度問い直す。

- **この自由度は、本当に必要とされているか** — 設定の組み合わせを許しているが、実際に使われるのは数通りではないか（要求へ返す）
- **この状態は、持つ必要があるか** — 状態を減らす、あるいは状態を外に出せないか（設計へ返す）
- **これは実行時に確認する必要があるか** — 型、制約、スキーマ、不変条件で、起こりえなくできないか（実装・静的検査へ返す）
- **壊れたときに検知できればよいのではないか** — 事前にすべてを確認するより、可観測性とアラートで十分な箇所はないか（運用へ返す）
- **そもそも作らない選択はあるか**

そのうえで、返しきれなかった分だけをテストで受け止める。

この判断を記録に残すこと（「この組み合わせは設計上起こりえないのでテストしない」）が、後からの読み手にとって重要になる。

## Consequences

得られること:

- テスト件数だけでなく、**システムの複雑さそのもの**が減ることがある
- 「テストできないほど複雑」という状態を、設計の問題として可視化できる
- テストしない判断に根拠が残る

失うこと・副作用:

- 設計変更のコストと、合意形成の時間がかかる
- 工程やチームをまたいだ提案になるため、摩擦が生じやすい
- タイミングを逃すと、単なる手戻りになる（早い段階ほど効く）

効かない場面:

- 外部システムや法令で、組み合わせの自由度が外から決まっている場合
- リリース直前で、設計変更のリスクのほうが大きい場合
- 変更の権限を持つ人に話が通らない構造になっている場合（この場合、記録に残して次の機会に回すほうが現実的）
