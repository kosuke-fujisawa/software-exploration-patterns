# 失敗状態から戻る

> このパターンは検証されていません。反例や、適用できなかった状況の報告を歓迎します。

「どんなテストをするか」から考えるのではなく、**「何が起きたら困るのか」**という Failure State を先に置き、そこから原因・条件・必要な保証へ遡る。

## Context

- 機能一覧や仕様項目を上から順にテスト設計しようとしている
- 網羅しようとすると件数が膨らむ一方で、本当に重要なものが埋もれている感覚がある
- 何を優先すべきかの根拠が「全部やる」以外に見つからない

## Problem

機能から出発すると、**テストは仕様の構造を反映するが、リスクの構造を反映しない**。

結果として、

- 重大な失敗と、軽微な失敗が、同じ粒度で確認される
- 仕様に書かれていない失敗（データが静かに壊れる、二重に請求される、復旧できない）が視野に入らない
- 「このテストは何を守っているのか」が説明できない

## Forces

- 機能一覧は与えられているが、失敗の一覧は与えられていない
- 「何が起きたら困るか」は、立場によって答えが違う（利用者、運用者、経営、規制当局）
- 困りごとを具体的に言語化するのは、機能を列挙するより難しい
- 失敗を想像する作業は、悲観的だと受け取られることがある

## Solution

Failure State（起きてほしくない状態）を先に言語化し、そこから遡る。

1. **何が起きたら困るか**を、観測可能な状態として書く（「使いにくい」ではなく「受付が完了したと表示されたのに、予約が登録されていない」）
2. その状態は**誰にとって、どれくらい困るか**を考える（取り返しがつくか、気づけるか、件数はどれくらいか）
3. その状態が**どういう条件で起きうるか**を遡る（入力、タイミング、同時実行、障害、運用操作、データ移行）
4. その条件に対して、**どの手段で守るのが妥当か**を決める（要求変更、設計変更、静的検査、テスト、可観測性、運用手順、モニタリング）
5. テストで守る分だけを、テストとして設計する

「何が起きたら困るか」が誰にも答えられない場合、それは**まだ守るべきものが合意されていない**という発見であり、テスト設計以前の問題として扱う。

## Consequences

得られること:

- テストの一つひとつが「何を守っているか」で説明できるようになる
- 仕様に書かれていない失敗（データ破損、二重処理、復旧不能）が視野に入る
- テスト以外の手段のほうが適切な箇所が見える
- 優先順位の議論が、好みではなく影響の大きさで行える

失うこと・副作用:

- Failure State の洗い出しに、最初のまとまった時間が要る
- 想像力に依存するため、思いつかなかった失敗は漏れる（機能からの網羅と併用する価値がある）
- 悲観的な議論が続くと、場の空気が重くなることがある

効かない場面:

- 失敗の影響が十分に小さく、網羅的に確認したほうが速い小規模な対象
- 探索的に作って捨てる段階のプロトタイプ
- Failure State の合意形成に関わる人を集められない状況（ただし、集められないこと自体が重要な情報）
